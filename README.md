# nobehong jailbreak

PS4 kernel exploit for firmware **13.52, 14.00 and 14.02**.

Open `index.html` on the PS4 browser, pick a payload, press DEPLOY.

## Which payload

| firmware | payload | note |
| --- | --- | --- |
| 13.52 | ps4-hen or GoldHEN | both have real tables for it |
| 14.00 | ps4-hen or GoldHEN | |
| 14.02 | **ps4-hen only** | `nova1402.bin`, loaded automatically |

GoldHEN cannot run on 14.02: its image is 14.00's, its step table is a list of
14.00 addresses, and its BSS window (`rvaPad 0xb3c000`) is the only 14.02
number in it that happens to still be right. The site refuses to start it
there rather than driving fifteen calls into the wrong functions.

## What was actually verified for 14.02, and how

The chain has three parts, and they are not equally proven. This is the
honest accounting.

**Kernel stage — verified offline, byte for byte.** `afterglow.js` carries its
own 14.02 table: five offsets, fifteen patch sites, one 142-byte bootstrap.

* The fifteen patch sites were checked against two decrypted 14.02 kernel
  images. Fourteen of them sit at the same RVA as 14.00; the last moved by
  +0x300.
* Six of them, and every field of the bootstrap, were additionally checked
  against a **pre-patch** dump taken from a console that had only ever run the
  leak half. Across the 2,686,976 bytes that dump covers, exactly 52 bytes
  differ from the post-patch image, in 26 runs, and every run is a patch site,
  the bootstrap's 0x490 field, or an ASLR pointer the dump stored as a full
  kernel address. That difference is what turns "the table looks plausible"
  into "these are the bytes a real 14.02 kernel ended up with".
* The bootstrap decodes linearly to 142 bytes, ends in `ret`, and each of its
  seven writes that the dumps preserve matches the post-patch image exactly.
  The two sysent writes fall past the end of the text dump and are pinned by
  symbol instead: `SYSENT` is `0x1102b70` on both 14.00 and 14.02.
* `swap_rbp` is `0x0a81478` because `4e 95 c3` occurs exactly once in the whole
  13.6 MB text image, there. `padding` is `0x0b3a4c0` because that is where the
  zero run behind kernel text starts, and both ends of that run cross-check
  against values already in the file — GoldHEN's `rvaPad 0xb3c000` is inside
  it, and its RW window ends 0x28 before the run does.
* A uniform shift is not used and must not be: 14.02 moved by five different
  deltas (0x0, 0x300, 0x370, 0x3f0, 0x480), and one shift fits at most seven
  of the seventeen sites.

**WebKit half — proven on hardware.** It is 14.00's, which is not a guess: a
14.02 console ran it and reached the kernel pointer leak. That is where the
anchor came from. If the WebKit build had moved, no leak would have come out.

**Enabler — verified offline, never run on hardware.** `nova1402.bin`
(sha256 `e9a0c329…e84537`) is the ps4-hen installer rebuilt against the 14.02
kernel table. Its sixteen patch sites sit on the opcodes their patch transforms
(`77 47`→`eb 47`, `75 0f`→`eb 0f`, a call→`xor eax,eax; jmp`, a prologue→
`b0 01 c3`, `0x800D0203`→zero, `09`→`40`), its firmware gate accepts 14.02, and
all seventeen of its embedded constants resolve from the verified table. It has
not been executed on a console. Nothing in this repository has.

## Reading the log

The run page takes diagnostics through the query string.

* `?afterglow=leak` — derive and verify the kernel base, then stop. Writes
  nothing.
* `?afterglow=probe` — fire nothing at all.
* `?stop=1` on the landing page — do not autostart, so a diagnostic can be
  reached with a real referrer.

A full run prints its steps as `[0]`…`[10]`. `[8]` is the one that matters for
14.02: it re-reads every patch site after writing it and refuses to continue
unless all fifteen are in place, so a wrong table cannot report success while
having written nothing.

## Files

```
index.html          landing page: payload picker, autostart
jb.html             run page
launch.js           the picker's logic, and the only place a run is started
jb.js               WebKit stage: primitives, module bases, dispatch to afterglow
core.js, mem.js     the WebKit exploit and the memory interface it leaves behind
int64.js            the 64-bit helper all of the above use
ps4_offsets.js      per-firmware WebKit offsets, one entry per firmware
afterglow.js        the kernel stage: leak, bootstrap, patches, teardown, payload
nova.bin            ps4-hen enabler, 14.00
nova1402.bin        ps4-hen enabler, 14.02
goldhen.bin         GoldHEN, 14.00 (refused on 14.02)
patchset-1400.bin   kernel patch set for the GoldHEN path, 14.00
patchset-1352.bin   the same, 13.52
cache.appcache      generated by make-manifest.sh -- regenerate after any edit
```

`nova.bin` and `hen.bin` are the same file under two names; `hen.bin` is kept
because older links point at it.

## Contributing a firmware

Every address in `afterglow.js` is firmware specific, and the fields are not
interchangeable. A firmware needs, at minimum: the anchor the leak hands back,
a `xchg rbp,rax ; ret` gadget that is unique in text, `prison0`, `rootvnode`,
the start of the zero run behind kernel text, the fifteen patch sites, and a
bootstrap whose writes match what a patched kernel of that version actually
contains. `setFirmware` refuses to run a firmware that has no patch table or no
bootstrap, rather than running one with 14.00's.
